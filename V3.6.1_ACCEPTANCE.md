# OPSIQO HCM v3.6.1 Production Closure Bootstrap — Acceptance Checklist

## A. Lockfile bootstrap and human review
- [ ] Run **OPSIQO v3.6.1 Reviewed Lockfile Bootstrap** from the exact source commit intended for release.
- [ ] Type `GENERATE_LOCKFILE` explicitly; the workflow must not auto-commit or push.
- [ ] `npm install --package-lock-only --ignore-scripts` succeeds on the protected network-enabled runner.
- [ ] `node scripts/review-lockfile.mjs` reports `readyForHumanReview=true`.
- [ ] Root package name/version and all direct dependency/devDependency specs match `package.json` exactly.
- [ ] No insecure HTTP or local file/link dependency is present in the generated lockfile.
- [ ] Reviewer inspects `package-lock.json`, `artifacts/lockfile-review.json`, `artifacts/npm-tree.json`, and `artifacts/package-lock.patch`.
- [ ] Reviewer confirms the lockfile SHA-256 and source commit in the workflow artifact.
- [ ] Reviewer places the approved `package-lock.json`, regenerates `SOURCE_MANIFEST.sha256` using `npm run source:manifest:generate`, reviews both, and commits them through normal source-control review; no workflow auto-commit is used.
- [ ] `npm run source:manifest:verify` passes and rejects unlisted extra release files.

## B. Protected dependency/build closure
- [ ] `npm ci` succeeds from the committed reviewed lockfile.
- [ ] `npm audit --audit-level=high` passes or approved exceptions are documented outside the application release gate.
- [ ] dedicated Gitleaks gate passes.
- [ ] CodeQL analysis passes.
- [ ] OPSIQO bounded source/secret scan passes.
- [ ] CycloneDX SBOM is generated from the reviewed lockfile.
- [ ] `npm run release:gate` passes completely.
- [ ] `npm run typecheck` passes.
- [ ] complete Vitest suite passes.
- [ ] Firebase Emulator Rules tests pass.
- [ ] Next.js production build passes.
- [ ] AI evaluation and AI governance checks pass.
- [ ] production preflight passes.
- [ ] authenticated deployed Lifecycle UAT passes.

## C. Cloud DR evidence closure
- [ ] GitHub OIDC/WIF authentication succeeds using the approved cloud evidence service account.
- [ ] production Firestore database identity is captured.
- [ ] PITR state is captured from the production database.
- [ ] scheduled-backup metadata is captured.
- [ ] latest READY backup is bound to the exact production database resource.
- [ ] operator types `RESTORE_TEST` before the controlled restore exercise.
- [ ] restore creates a new temporary database and does not overwrite production.
- [ ] configured non-sensitive sentinel hash verifies in the restored database.
- [ ] measured RTO and RPO satisfy the approved targets or the evidence bundle remains non-ready.
- [ ] temporary restored database is deleted and cleanup is evidenced.

## D. Final evidence chain
- [ ] production build archive SHA-256 is recorded.
- [ ] source manifest is verified.
- [ ] package-lock SHA-256 is recorded.
- [ ] committed lockfile-review artifact is regenerated in protected CI and SHA-256 bound into the evidence bundle.
- [ ] SBOM and provenance hashes are recorded.
- [ ] cloud DR and restore-exercise evidence hashes are recorded.
- [ ] final `production:evidence:verify` reports ready.
- [ ] production promotion references the exact reviewed CI evidence URL/run.

## Decision boundary
A green v3.6.1 evidence bundle is release-specific operational evidence. It is not a legal/compliance certification, a SLSA-level claim, a guarantee of future recoverability, or proof that every external dependency can meet the same RTO/RPO.
