## 3. JIT boundary validation
Verified source gates:
- Existing active organization membership is recognized before new-user JIT creation checks.
- New JIT requires an authenticated **verified email claim**.
- New JIT requires an existing **active worker** matched through governed work-email evidence.
- Provider must be active and must match the Firebase sign-in provider ID.
- Email domain must be explicitly allowed by the provider.
- Provider MFA and managed-device requirements are enforced when configured.
- Automatic activation requires `jitMode=employee_only`.
- Automatic activation requires **at least one explicit matching mapping**.
- **Every matching automatic mapping must resolve to `employee` and be `autoJitEligible=true`.**
- Mapping schema prohibits automatic JIT for manager/HR/admin roles.
- Anything outside the narrow employee-only boundary creates an independently reviewed access request rather than privileged automatic access.
- Sign-in JIT calls include Firebase App Check evidence when App Check is configured.

## 5. Access review, reconciliation and provisioning controls
- Access grant/change/disable/reactivate requests require approval before execution.
- Creator/submitting reviewer/self-target approval controls are enforced.
- Access review cannot close with pending items.
- Revoke decisions produce governed access requests rather than silent membership mutation.
- Identity reconciliation separately measures active memberships, active external identities, unlinked memberships, orphan identities and active identities associated with inactive membership evidence.
- Dashboard no longer infers inactive-membership identities from missing worker links; it uses reconciliation evidence.
- SCIM provisioning requests require an outbound `scim_users` integration profile.
- Native v3.3 execution is deliberately bounded to independently approved **SCIM create** provisioning.
- SCIM update/disable fails closed pending a deployment-specific safe remote-resource addressing implementation.
- Provisioning continues through v3.2 governed integration run/staging/idempotency controls.

## 6. Privacy / evidence minimization
- Raw external identity subjects are server-only and removed from dashboard responses.
- Session assurance persists a UID hash, role/provider and MFA/device observations; it does not persist ID tokens, refresh tokens, passwords or SAML assertions.
- AI Copilot integration receives only aggregate identity readiness/exception counts when the actor has `identity.read`.
- Aggregate AI evidence excludes passwords, tokens, raw external subjects and individual access-review rationales.

## 11. Known limitations
1. No trusted npm lockfile/dependency build could be produced in this execution environment.
2. Live enterprise OIDC/SAML end-to-end sign-in requires deployment-specific Firebase/Identity Platform and IdP configuration and therefore was not externally executed here.
3. SAML XML signature/certificate assertion validation is not reimplemented inside OPSIQO; the configured federation platform performs that protocol security function.
4. SCIM create is the only native provisioning operation executed by v3.3; update/disable remains a governed request until a safe deployment adapter can identify the remote resource.
5. Identity readiness and reconciliation are operational governance indicators, not legal/security certifications.
