# OPSIQO HCM v3.6 Production Acceptance — Evidence Closure & Cloud Disaster Recovery

## A. Trusted dependency and build evidence
- [ ] A reviewed `package-lock.json` is generated from the approved npm registry, committed, and included in `SOURCE_MANIFEST.sha256`.
- [ ] `sha256sum -c SOURCE_MANIFEST.sha256` passes before dependency installation.
- [ ] `npm ci` succeeds from that exact lockfile.
- [ ] `npm audit --audit-level=high` passes or every release-blocking exception has independent approval and retained evidence.
- [ ] Dedicated Gitleaks secret scanning passes in protected CI.
- [ ] GitHub CodeQL JavaScript/TypeScript analysis completes without an unresolved release-blocking finding.
- [ ] The bounded OPSIQO static source scan passes; it is not used as a substitute for Gitleaks/CodeQL.
- [ ] CycloneDX lockfile inventory is generated from the reviewed lockfile.
- [ ] Typecheck, unit/integration tests, Firestore Rules tests, production build, AI evaluation/governance, production preflight and integrated deployed UAT all pass.
- [ ] Build provenance and packaged build artifact are retained from the same traceable CI run.

## B. Cloud Firestore backup / PITR evidence
- [ ] Production cloud evidence is captured through GitHub OIDC/Google Workload Identity Federation, not a checked-in cloud key.
- [ ] `gcloud firestore databases describe` evidence is retained for the exact production database.
- [ ] The approved policy states whether PITR is required and whether scheduled backups are required.
- [ ] If PITR is required, captured database metadata reports `POINT_IN_TIME_RECOVERY_ENABLED`.
- [ ] If scheduled backups are required, at least one backup schedule is observed.
- [ ] If scheduled backups are required, at least one `READY` backup is observed and its age is within `OPSIQO_CLOUD_DR_MAX_BACKUP_AGE_HOURS`.
- [ ] Backup readiness/freshness evidence and restore selection are bound to the exact production Firestore database resource, not another database in the project.
- [ ] Raw cloud metadata and the derived `opsiqo-cloud-dr-evidence.json` are retained together.

## C. Controlled restore / DR exercise
- [ ] The restore workflow is manually authorized with the exact confirmation `RESTORE_TEST` in the protected `production-evidence` environment.
- [ ] The workflow restores the latest READY production backup into a new temporary database; it never restores over the active production database.
- [ ] A deliberately non-sensitive recovery-sentinel document path is configured.
- [ ] The expected canonical JSON SHA-256 of the sentinel is stored as protected CI evidence and is not inferred from the restored database.
- [ ] The restored sentinel exists and its canonical SHA-256 matches the approved expected digest.
- [ ] Actual RTO is measured from restore initiation to successful sentinel verification.
- [ ] Actual RPO is measured from backup snapshot time to exercise start.
- [ ] Actual RTO/RPO meet the approved targets for the exercised plan.
- [ ] The temporary restored database is deleted and cleanup is verified before the exercise is considered fully passing.
- [ ] Exercise results are independently reviewed in the governed Platform Reliability / DR process.

## D. Production evidence bundle
- [ ] `opsiqo-production-evidence.json` is generated only after all required technical gates pass.
- [ ] The bundle identifies release version, source commit and a traceable CI workflow run.
- [ ] SHA-256 values bind the reviewed lockfile, source manifest, SBOM, provenance, packaged build, cloud-DR evidence and DR-exercise evidence.
- [ ] `npm run production:evidence:verify` passes against the retained local artifacts.
- [ ] Production configuration references the approved CI bundle, cloud-DR evidence and DR-exercise evidence through `OPSIQO_PRODUCTION_EVIDENCE_REF`, `OPSIQO_CLOUD_DR_EVIDENCE_REF` and `OPSIQO_DR_EXERCISE_EVIDENCE_REF`.
- [ ] Evidence references are treated as traceability metadata; their presence alone is not treated as proof.

## E. Firebase Admin authentication
- [ ] `OPSIQO_FIREBASE_ADMIN_AUTH_MODE` is explicitly set to `service_account` or `adc`.
- [ ] Managed Google workloads / GitHub cloud-evidence workflows prefer `adc`/Workload Identity Federation where operationally supported.
- [ ] If `service_account` mode is used, the key is injected through a deployment secret manager and never committed.
- [ ] `gha-creds-*.json` remains excluded from the repository and release package.

## F. Release and runtime readiness
- [ ] `OPSIQO_RELEASE_VERSION=3.6.0`.
- [ ] Existing App Check, privileged MFA, document-scan, regulatory-source, Integration, Identity, Security Operations, governed-AI and Platform Reliability controls remain satisfied where enabled.
- [ ] `OPSIQO_ENABLE_PLATFORM_RELIABILITY=true`.
- [ ] `OPSIQO_BACKUP_EVIDENCE_MODE` accurately identifies the approved evidence model.
- [ ] `OPSIQO_PLATFORM_MONITORING_SOURCE` identifies the authoritative monitoring source.
- [ ] `/api/health/ready` and `npm run preflight:production` fail closed if v3.6 production evidence references are missing.

## G. Decision / assurance boundary
- [ ] A green v3.6 evidence bundle is described as release-specific evidence closure, not certification of security, SLSA level, legal compliance, guaranteed availability or permanent DR capability.
- [ ] A successful restore exercise applies only to the tested backup, sentinel, path and execution time.
- [ ] Platform/security evidence cannot independently discipline, terminate, rank, compensate or otherwise determine an employee outcome.
