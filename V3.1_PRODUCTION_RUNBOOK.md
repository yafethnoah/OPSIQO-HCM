# OPSIQO HCM v3.1 Production & Rollback Runbook

## Promotion prerequisites
Production promotion is prohibited until the reviewed `package-lock.json` exists and all v3.1 acceptance/build gates pass in CI. Do not convert source/static validation into a production certification.

## Build verification
```powershell
npm ci --registry=https://registry.npmjs.org --no-audit --no-fund
npm run release:gate
npm run typecheck
npm test
npm run test:rules
npm run build
npm run ai:evaluate
npm run ai:governance-check
npm run preflight:production
```

## Integration production configuration
If external integrations are enabled:
```text
OPSIQO_ENABLE_EXTERNAL_INTEGRATIONS=true
OPSIQO_INTEGRATION_HOSTS=<comma-separated exact approved public hosts>
```
Keep connector credentials in the organization-approved secret provider. OPSIQO connector records must contain references only.

## Deployment order
1. Back up/export production configuration and record the current release/commit.
2. Review Firestore Rules and indexes.
3. Deploy Rules/index changes.
4. Deploy application build produced by the verified CI run.
5. Confirm `/api/health` and `/api/health/ready`.
6. Run authenticated `npm run uat:lifecycle` against the deployed environment.
7. Verify `/integrations` and `/api/organizations/<orgId>/integrations/dashboard` for an authorized HR/Admin role.
8. Run only synthetic/non-consequential connector tests first.
9. Verify staging-only behavior, dead-letter handling and reconciliation.
10. Capture CI/UAT evidence in the Enterprise HCM release assessment before promotion approval.

## Integration incident response
- Pause the affected connector rather than deleting evidence.
- Preserve integration run, dead-letter, reconciliation, event and audit records.
- If credentials may be exposed, rotate them in the external secret provider; do not write the replacement value into OPSIQO.
- If unexpected data crossed the boundary, invoke the Privacy/AI incident workflow and qualified review process.
- Do not replay data until the contract, source/target system state and idempotency implications are understood.

## Rollback
1. Pause external connectors if data correctness is uncertain.
2. Roll application traffic back to the prior verified release.
3. Do not delete v3.1 server-only integration evidence created during the failed release.
4. Restore compatible Rules/indexes only after confirming older application behavior.
5. Reconcile source/target record counts before replaying any failed exchange.
6. Record the rollback, root cause, remediation and evidence reference in the Enterprise HCM release assessment/action workflow.

## Non-negotiable boundary
Rollback/replay tooling must not bypass source-module employment controls. Staged integration records cannot directly authorize worker-level changes.
