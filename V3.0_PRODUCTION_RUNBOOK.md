# OPSIQO HCM v3.0 Production & Rollback Runbook

## Promotion prerequisites
Production promotion is blocked until `package-lock.json` is committed/reviewed and all dependency-aware gates pass. The v3.0 in-app release assessment mirrors these gates, requires a traceable CI evidence reference for production, and does not replace CI evidence.

## Build / verification
```powershell
npm ci --registry=https://registry.npmjs.org --no-audit --no-fund
npm run release:gate
npm run typecheck
npm test
npm run test:rules
npm run build
npm run ai:evaluate
npm run ai:governance-check
npm run preflight:production
```

## Deployment candidate UAT
Set protected values for `OPSIQO_UAT_BASE_URL`, `OPSIQO_UAT_ORG_ID`, `OPSIQO_UAT_ID_TOKEN` and `OPSIQO_UAT_APP_CHECK_TOKEN`, then run:
```powershell
npm run uat:lifecycle
```
The suite includes the Enterprise HCM Command Center route and the AI consequential-use server guard.

## Production environment controls
At minimum verify Firebase project/bucket consistency, Admin credentials, HTTPS URLs, App Check, privileged MFA, clean-document scanning, automation and survey secrets, regulatory-source host allowlist, governed non-demo AI configuration and provider credentials. `/api/health/ready` must return HTTP 200 before promotion.

## Command Center post-deploy checks
1. Open `/dashboard` as HR Admin and verify all permitted domain nodes.
2. Open `/dashboard` as HR Partner; verify read/manage/audit but no approval actions.
3. Verify a Manager/Employee receives the Lifecycle fallback rather than enterprise data.
4. Save a data-quality snapshot and confirm an audit log was written.
5. Create/submit a test SLO in non-production and verify independent approval.
6. Record a deliberately incomplete release assessment and confirm gate=`blocked` and approval is unavailable.
7. Run `npm run commandcenter:review` for a test organization and verify deduplicated notifications.

## Incident response
If v3.0 dashboard aggregation fails, source HCM modules remain independently accessible. Disable Command Center navigation/feature exposure if required while preserving source modules. Do not bypass Firestore Rules or grant broader client access to Command Center collections.

## Rollback
1. Stop promotion/automation affecting the candidate release.
2. Redeploy the last known-good application image/commit.
3. Restore the previous Firestore Rules only if compatibility requires it; server-only v3.0 collections can safely remain inaccessible.
4. Do not delete Command Center audit/action/report records during rollback; retain them for investigation.
5. Verify `/api/health`, `/api/health/ready`, authentication, Lifecycle, AI guardrails and critical HR workflows.
6. Document the rollback reason and open a governed enterprise action before reattempting promotion.
