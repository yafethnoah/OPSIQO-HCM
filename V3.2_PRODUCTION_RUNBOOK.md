# OPSIQO HCM v3.2 Production & Rollback Runbook

## Promotion prerequisites
Production promotion is prohibited until a reviewed `package-lock.json` exists and all v3.2 build, Rules, security, AI-governance, runtime and UAT gates pass in CI. Source/static validation is not production certification.

## Build verification
```powershell
npm ci --registry=https://registry.npmjs.org --no-audit --no-fund
npm run release:gate
npm run typecheck
npm test
npm run test:rules
npm run build
npm run ai:evaluate
npm run ai:governance-check
npm run preflight:production
```

## Production integration configuration
If outbound/external connectors are enabled:
```text
OPSIQO_ENABLE_EXTERNAL_INTEGRATIONS=true
OPSIQO_INTEGRATION_HOSTS=<comma-separated exact approved public hosts>
OPSIQO_WEBHOOK_MAX_BODY_BYTES=1048576
```

Use exact host names; do not place URLs, credentials or wildcards in `OPSIQO_INTEGRATION_HOSTS`.

### Secrets
Built-in v3.2 runtime resolution supports `env://NAME`. Connector records store the reference only. Deployment-specific providers such as GCP Secret Manager, Azure Key Vault, AWS Secrets Manager or Vault require an explicitly implemented provider adapter; unsupported references fail closed. Do not place secret values in Firestore, UI fields, logs, CI evidence or source control.

### SFTP
The source tree defines a governed SFTP runtime-provider interface but does not bundle a network SFTP client. SFTP profiles must remain inactive unless the deployment registers and tests an approved provider. Do not bypass this fail-closed control with ad-hoc shell or child-process execution.

## Deployment order
1. Back up/export production configuration and record the current release/commit.
2. Review Firestore Rules, Storage Rules and indexes.
3. Review approved connector/contract/adapter profiles and the production host allow-list.
4. Deploy Rules/index changes.
5. Deploy the application artifact from the verified CI run.
6. Confirm `/api/health` and `/api/health/ready`.
7. Run authenticated `npm run uat:lifecycle` against the target environment.
8. Verify `/integrations`, integration dashboard and runtime dashboard with an authorized HR/Admin role.
9. Run sandbox validation with synthetic/non-consequential data and verify endpoint/body-size limits.
10. Activate one low-risk inbound connector first and confirm staging/dead-letter/reconciliation behavior.
11. Activate schedules only after manual execution and circuit/retry behavior are verified.
12. Enable signed webhook ingress only after the source system, timestamp convention and HMAC secret are confirmed.
13. Capture CI/UAT/runtime evidence in the Enterprise HCM release assessment before production approval.

## Scheduler operation
Run the governed scheduler in a single controlled job definition; the service also uses a time-bounded lease to protect against overlap:
```powershell
$env:OPSIQO_JOB_ORG_ID="YOUR_ORG_ID"
npm run integration:runtime
```
Do not schedule more frequently than operationally justified. Each scheduled occurrence uses a deterministic idempotency key in addition to the scheduler lease. Scheduled outbound profiles remain prohibited from automatically sourcing HCM domain records in v3.2.

## Signed webhook operation
The public webhook endpoint uses the organization ID and connector code in the route. Configure the source system to send:
- the exact raw JSON body;
- the configured timestamp header/value expected by the integration;
- the HMAC-SHA256 signature over `timestamp + "." + rawBody`;
- a timestamp expressed in Unix milliseconds and within the allowed skew.

Rejected signatures and stale timestamps must be investigated rather than retried blindly. Duplicate completed deliveries return the existing receipt/run result idempotently; concurrent deliveries are blocked by a short processing lease, while failed/stale claims may be retried within the timestamp window.

## Integration incident response
- Pause the affected adapter/connector/schedule rather than deleting evidence.
- Preserve integration run, staging metadata, dead-letter, reconciliation, runtime state, webhook receipt, replay and audit records.
- If credentials may be exposed, rotate them in the external secret provider and update only the reference if necessary.
- If unexpected personal information crossed the boundary, invoke the Privacy/AI incident workflow and qualified review process.
- If a circuit opens, identify whether the cause is remote availability, authentication, contract drift, endpoint policy, mapping or data quality before resetting/retrying.
- Do not replay an exchange until source/target state, idempotency implications and contract compatibility are understood.

## Rollback
1. Pause schedules and active adapters/connectors if correctness is uncertain.
2. Roll application traffic back to the prior verified release.
3. Preserve v3.2 server-only runtime evidence; do not delete runs, webhook receipts or replay records to make metrics appear healthy.
4. Restore compatible Rules/indexes only after confirming prior-release behavior.
5. Reconcile source/target state before replaying any failed exchange.
6. Rotate/revoke webhook or connector secrets if trust may have been lost.
7. Record rollback cause, affected integrations, reconciliation results and remediation evidence in the Enterprise HCM release assessment.

## Non-negotiable boundary
Runtime execution, scheduler jobs, replay tools and webhooks cannot bypass source-module HCM controls. Staged integration data never independently authorizes hiring, termination, compensation, succession, promotion, discipline, accommodation, emergency deployment or another individual employment outcome.
