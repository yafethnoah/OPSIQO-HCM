# OPSIQO HCM v3.2 Production Acceptance Checklist

## Dependency/build gate
- [ ] Generate and review `package-lock.json` from the approved npm registry.
- [ ] Commit the reviewed lockfile and use `npm ci` thereafter.
- [ ] `npm run release:gate` passes.
- [ ] `npm run typecheck` passes.
- [ ] `npm test` passes.
- [ ] `npm run test:rules` passes.
- [ ] `npm run build` passes.
- [ ] `npm run ai:evaluate` passes.
- [ ] `npm run ai:governance-check` passes.
- [ ] `npm run preflight:production` passes.
- [ ] `npm run uat:lifecycle` passes against the target environment.
- [ ] Production promotion evidence includes a traceable CI/workflow reference.

## Adapter profile governance
- [ ] Adapter profile creator/submitting reviewer cannot independently approve activation.
- [ ] Active runtime profiles reference only an approved/active connector and approved/active contract.
- [ ] REST/SCIM resource paths are relative and cannot pivot to another origin.
- [ ] REST pull uses GET; REST/SCIM push uses a non-GET method.
- [ ] Webhook adapters require a webhook connector with `hmac_secret` authentication.
- [ ] File/SFTP paths remain connector-scoped and reject traversal.
- [ ] SFTP activation fails closed unless a deployment-approved SFTP provider is registered.

## Credential and endpoint security
- [ ] Connector records contain secret references only; no inline credential is persisted.
- [ ] Built-in secret resolution is restricted to approved `env://NAME` references; other provider references fail closed unless a deployment provider is implemented.
- [ ] HTTPS/SFTP endpoints reject embedded credentials, localhost, private/non-public IPs and production hosts outside `OPSIQO_INTEGRATION_HOSTS`.
- [ ] OAuth token endpoints receive the same public-host/allow-list validation as connector endpoints.
- [ ] Redirects are not automatically followed across trust boundaries.
- [ ] Inbound HTTP responses and outbound runtime payloads are bounded to 5 MB; OAuth token responses are separately bounded.
- [ ] Dangerous user-supplied headers are rejected.

## Runtime reliability
- [ ] Connector-scoped run idempotency persists only a SHA-256 idempotency hash, never the plaintext key.
- [ ] Retry policy is bounded and terminal non-2xx responses fail the run rather than becoming data.
- [ ] Circuit breaker opens and resets according to the governed adapter profile.
- [ ] Scheduler claims are protected by a time-bounded lease to prevent concurrent execution.
- [ ] Each scheduled occurrence uses a deterministic idempotency key so a retried scheduler cycle reuses/recognizes the prior run rather than creating an uncontrolled duplicate.
- [ ] Delta/cursor/ETag state is stored server-side and updated only after governed execution.
- [ ] Scheduled outbound execution cannot automatically source HCM domain records.
- [ ] Outbound payload hashes represent the staged/sent payload, not merely a remote response.
- [ ] A rejected staging record does not prematurely terminate an otherwise active batch.

## Signed inbound webhooks
- [ ] Webhook requests use HMAC-SHA256 with a server-resolved secret.
- [ ] Signature input includes the supplied timestamp and exact raw request body.
- [ ] Timestamp skew is bounded and a server-only signature index prevents duplicate processing; completed duplicate deliveries return the prior result idempotently.
- [ ] Webhook body size is bounded before parsing.
- [ ] Raw webhook bodies and signatures are not persisted in operational receipts; failed processing records only bounded error metadata.
- [ ] A time-bounded processing lease permits controlled retry after a failed/stale processing claim without permitting concurrent duplicate processing.
- [ ] Accepted webhook data is still staged; no webhook can directly mutate consequential HCM records.

## Mapping / contract boundary
- [ ] Field mappings are deterministic and use the approved contract/profile configuration.
- [ ] Required mappings fail closed when source fields are missing.
- [ ] Runtime contract validation remains the documented `opsiqo-json-schema-subset-v1` rather than an unsupported full-spec claim.
- [ ] Invalid inbound records create governed dead-letter evidence without persisting rejected payload content.

## Replay / sandbox governance
- [ ] Replay creation and execution require governed approval and cannot bypass idempotency/domain authorization controls.
- [ ] Inbound replay re-stages prior server-side evidence; outbound replay uses staged data and cannot reconstruct worker data from source modules automatically.
- [ ] Sandbox execution uses synthetic/non-consequential data and persists only bounded evidence, not test credentials or arbitrary raw payloads.

## Consequential-use boundary
- [ ] Integration/runtime routes contain no direct Worker/Employment/Compensation/Recruiting/Separation/Succession mutation service import.
- [ ] Staging acknowledgement does not apply a payload to a source-of-record collection.
- [ ] Any eventual worker mutation is performed through the responsible HCM domain service and its existing authorization/business rules.
- [ ] Aggregate AI evidence contains no connector credentials, webhook bodies or staged worker payloads.

## Privacy/security
- [ ] All integration and runtime collections/indexes deny direct browser reads/writes.
- [ ] HR Partner does not receive `integration.approve`.
- [ ] Manager and Employee do not receive enterprise integration permissions.
- [ ] Production external integrations fail readiness closed without the exact egress-host allow-list.

## Enterprise integration
- [ ] Runtime failures/circuit state appear in the Integration Command Center.
- [ ] Integration runtime risk contributes to Lifecycle and Enterprise HCM readiness.
- [ ] Aggregate-only integration/runtime evidence is available to the governed AI Copilot only with `integration.read`.
- [ ] `/integrations/dashboard` and `/integrations/runtime/dashboard` are included in lifecycle UAT.
- [ ] `npm run integration:runtime` is configured as a controlled scheduler job when runtime schedules are used.
