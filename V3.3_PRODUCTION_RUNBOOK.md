# OPSIQO HCM v3.3 — Production & Rollback Runbook

## Promotion prerequisites
Production promotion is prohibited until `V3.3_ACCEPTANCE.md` is satisfied and traceable CI evidence exists. A reviewed `package-lock.json` is mandatory.

## Required production controls
```env
NODE_ENV=production
OPSIQO_RELEASE_VERSION=3.3.0
OPSIQO_REQUIRE_APP_CHECK=true
OPSIQO_REQUIRE_ADMIN_MFA=true
OPSIQO_REQUIRE_CLEAN_DOCUMENT_SCAN=true
OPSIQO_REQUIRE_GOVERNED_AI_CONFIG=true
OPSIQO_ENABLE_ENTERPRISE_SSO=true
OPSIQO_IDENTITY_HOSTS=<exact-comma-separated-public-hosts>
OPSIQO_ALLOWED_ADMIN_PROVIDERS=<exact-firebase-provider-ids>
OPSIQO_PUBLIC_SSO_DISCOVERY=false
```

Retain all existing v3.2 integration, Firebase, regulatory, AI and security variables. Secrets must stay in the deployment secret manager.

## Federation rollout
1. Configure and test the OIDC/SAML provider in Firebase Authentication / Identity Platform.
2. Create matching OPSIQO provider as draft.
3. Run metadata validation.
4. Complete independent provider approval.
5. Activate only with a passing test not older than 30 days.
6. Create/approve mappings.
7. Pilot privileged sign-in with the explicit admin provider allow-list.
8. Pilot employee JIT with a small controlled group before broad enablement.

## Incident containment
If federation behavior is abnormal:
1. Pause the affected identity provider in OPSIQO.
2. Disable or pause the corresponding provider at the identity platform/IdP as appropriate.
3. Preserve audit logs, provider-test evidence and identity reconciliation snapshots.
4. Review recent membership/access-request changes.
5. Run identity reconciliation and access review.
6. Do not bulk-disable workers or employment records as an identity incident response shortcut.

## Suspected unauthorized JIT
1. Pause provider.
2. Capture reconciliation.
3. Identify affected memberships from audit evidence.
4. Create governed disable-membership requests where access must be revoked.
5. Require independent approval/execution.
6. Investigate work-email index, provider mapping, MFA/device claim and IdP configuration evidence.

## SCIM provisioning incident
1. Pause the SCIM adapter profile/connector in Integration Center.
2. Stop approved provisioning execution.
3. Inspect integration run, staging, dead-letter and idempotency evidence.
4. Reconcile external identity state before replay.
5. Use governed replay/repair processes; do not bypass staging with direct scripts against worker records.

## Rollback
Application rollback:
1. Redeploy the last approved v3.2/v3.3 artifact according to change-control policy.
2. Keep Firestore identity collections intact for audit evidence.
3. Disable `OPSIQO_ENABLE_ENTERPRISE_SSO` if federation entry must be removed during rollback.
4. Preserve provider configuration in paused state rather than deleting evidence unless approved retention policy requires deletion.
5. Re-run production readiness, UAT and identity reconciliation after rollback.

## Scheduled governance
```powershell
$env:OPSIQO_JOB_ORG_ID="YOUR_ORG_ID"
npm run identity:review
npm run integration:review
npm run integration:runtime
```

## Limitations
- OPSIQO validates OIDC discovery metadata and fingerprints SAML metadata; it does not independently certify the IdP or claim complete protocol conformance.
- SAML assertion/certificate/signature validation is delegated to the configured Firebase/identity-platform federation layer.
- v3.3 SCIM native execution is bounded to approved create provisioning. Update/disable requires a deployment-specific remote resource-addressing implementation.
- Identity readiness is operational assurance, not a legal/security certification.
