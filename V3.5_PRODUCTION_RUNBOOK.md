# OPSIQO HCM v3.5 Production & Disaster-Recovery Runbook

## 1. Promotion prerequisites
Production promotion is blocked until a reviewed `package-lock.json` exists and the protected CI workflow passes dependency install, high-severity npm audit gate, bounded source scan, SBOM generation, release gate, typecheck, tests, Firebase Rules tests, build, AI governance, production preflight and integrated UAT.

Required v3.5 runtime configuration:
```text
OPSIQO_RELEASE_VERSION=3.5.0
OPSIQO_ENABLE_PLATFORM_RELIABILITY=true
OPSIQO_BACKUP_EVIDENCE_MODE=<firebase_pitr|external_backup|governed_manual>
OPSIQO_PLATFORM_MONITORING_SOURCE=<approved-monitoring-source>
```
Existing Security Operations, Identity, Integration, Firebase App Check/MFA, regulatory egress and governed-AI production controls remain mandatory where enabled.

## 2. Supply-chain evidence
The protected CI workflow must retain:
- dependency installation evidence from the reviewed lockfile;
- `npm audit` result and any approved exception record;
- bounded OPSIQO static-scan result plus the organization's dedicated SAST/secret scan evidence;
- CycloneDX SBOM from the committed lockfile;
- packaged build artifact digest;
- generated build provenance and CI run/evidence reference.

Treat the OPSIQO-generated SBOM as lockfile inventory evidence and provenance as build traceability evidence. Do not claim complete CycloneDX/SLSA conformance or a SLSA level solely because these files exist.

## 3. Backup and restore operations
For each production data/service tier:
1. confirm an approved Platform Backup Policy with RPO/RTO and retention expectations;
2. confirm provider-side backup/PITR configuration outside OPSIQO;
3. retain immutable/provider evidence reference;
4. record backup evidence in OPSIQO;
5. perform a controlled restore test to an isolated target;
6. record integrity result and actual RTO/RPO;
7. require independent verification before evidence is treated as verified.

Never test destructive restore operations against the active production target.

## 4. Disaster recovery exercise
At least according to the approved plan cadence:
1. declare exercise scope and approved DR plan;
2. establish safe test boundaries and rollback;
3. exercise service restoration sequence and dependencies;
4. capture actual RTO/RPO, integrity and availability evidence;
5. record gaps and corrective actions;
6. independently review the exercise;
7. update the DR plan or risk/exception record as required.

## 5. Configuration drift
Configuration snapshots are compared only with an approved baseline. High/Critical drift requires review and evidence. If drift is caused by an authorized emergency change, link the incident/change evidence rather than silently normalizing the baseline.

## 6. Platform incident response
For Critical platform incidents:
- activate Security Operations/incident coordination where applicable;
- contain safely;
- preserve evidence and correlation references;
- recover using approved recovery procedures;
- record root cause and corrective actions;
- attach the independently reviewable postmortem;
- close only after independent approval.

Platform/security incidents are operational evidence and cannot independently become an employment finding or disciplinary outcome.

## 7. SLO monitoring
Approved SLOs must use the identified authoritative monitoring source. Record current availability/latency/error-budget evidence through governed updates. A breach creates review/action signals; it is not proof of negligence, compliance failure or employee performance failure.

## 8. Rollback
If v3.5 application deployment fails:
1. stop new promotion/deployment activity;
2. preserve logs, CI evidence and incident correlation IDs;
3. roll application traffic back to the last independently accepted release artifact;
4. do not roll back Firestore schema/data by destructive deletion;
5. if new Platform Reliability records exist, retain them as audit evidence;
6. verify `/api/health/ready`, authentication, Lifecycle dashboard and core HCM routes after rollback;
7. open a platform incident and corrective action if the failure was material.

## 9. Governance automation
Run for each production organization under the protected job identity:
```powershell
$env:OPSIQO_JOB_ORG_ID="YOUR_ORG_ID"
npm run platform:review
```
Review backup evidence, restore failures, overdue DR exercises, high-risk drift, Critical incidents, SLO breaches and High/Critical supply-chain findings.
